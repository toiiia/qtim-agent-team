# /qtim:design — дизайн-конвейер

> Читает только team-lead. Здесь — ведение конвейера в текущей сессии: порядок стадий,
> checkpoints, выбор трека, resume, спавн ролей. Контракты, переживающие сессию (схема
> артефактов `docs/design/<slug>/`, контракт показа, DS-гейт, handoff со статусом кода), —
> [`reference/design-pipeline.md`](../reference/design-pipeline.md); семантика статусов, slug и
> resume-механика — общие с PM-конвейером, канон в
> [`reference/feature-pipeline.md`](../reference/feature-pipeline.md). Charter-секция
> «Дизайн-конвейер» — производная сводка, при расхождении верен reference.

## Preconditions

1. Charter содержит секцию «Дизайн-конвейер» (дизайн-дорожка настроена setup'ом, Q0=Designer).
   Секции нет → **не веди конвейер**: сообщи, что дизайн-дорожка не настроена, и предложи
   повторный `/qtim:setup` — он дописывает, не пересоздаёт. Это fail-soft, не ошибка.
2. Прочитай [`../reference/design-pipeline.md`](../reference/design-pipeline.md) — контракты
   стадий; статусы и resume — по [`../reference/feature-pipeline.md`](../reference/feature-pipeline.md).
3. Существует `docs/design/<slug>/` с артефактами → это **resume**: продолжи с первой стадии,
   чей артефакт не в `Approved` и выше (механика — как у `/qtim:feature`). Набор артефактов
   сообщает трек: один `design-brief.md` с секцией концепта = fast-path.

## Argument

`$ARGUMENTS` — короткое имя для slug (kebab-case). Пусто — выведи из брифа и подтверди на
стадии 1.

## Выбор трека (после стадии 1)

- **Fast-path** — мелкая задача в одну фазу (баннер, секция лендинга, один экран без новых
  направлений): один документ `design-brief.md` (вводные + один концепт + критерий приёмки),
  один показ. Ни один триггер «развилки?» (`intake-protocol.md`) не сработал.
- **Полный конвейер** — новый продукт/раздел, выбор направления, дизайн-система, или сработал
  любой триггер «развилки?».

Обнаружил развилку внутри fast-path — разворачивай в полный конвейер: brief уже есть,
продолжай со стадии 2.

## Стадии полного конвейера

Checkpoint после стадий 1, 2, 3(цикл), 4, 5, 7. **Показ, сбор фидбека и утверждение ведёшь ты,
team-lead** — у ролей нет диалога с пользователем: роль готовит деливерабл и итерирует по уже
полученному фидбеку через `SendMessage`. После подтверждения переводи стадию в
`Approved` — иначе resume откатит конвейер на эту стадию. Статусы всех стадий ведёт
**таблица стадий в `design-brief.md`** — канон и причина в `design-pipeline.md`.

### 1. Intake → `docs/design/<slug>/design-brief.md`

Вводные возьми из charter (блок Qd setup) — не спрашивай их заново, спроси только
недостающее. Интервью порциями по 1-3 вопроса: тип продукта и платформа · аудитория продукта · **аудитория
показа и как собираем фидбек** (кто смотрит прототип, каким каналом возвращаются правки) ·
материалы — референсы, брендбук, скриншоты конкурентов, существующий сайт (запроси ссылки и
файлы; агентский research отдельной стадией не делается — материалы приносит пользователь,
точечный поиск дозволен по запросу). DS-target **не спрашивай** — он решается на стадии 4.
Checkpoint: сводка понимания + предложенный трек.

### 2. Направления → `docs/design/<slug>/directions/`

Спавни `designer` (режим DIRECTION): **2-3 статичных концепта ключевого экрана, радикально
разных** — по одному самодостаточному HTML-файлу на направление (открывается без сервера,
отправляется файлом). Вариантность — здесь, к направлениям; кликабельный прототип будет один.
Checkpoint: показ направлений → пользователь выбирает. Выбор зафиксируй в brief.

### 3. Токены → прототип → `docs/design/<slug>/prototype/`

Сначала `designer` (режим TOKENS): дистилляция **утверждённого направления** в токены
нейтрального формата — CSS-переменные + `tokens.json` (компилируется и в Figma variables, и в
тему кода). Токены появляются здесь, до прототипа: вход `proto` — концепт + токены.

Затем спавни `proto` (или продолжи `SendMessage`, если поднят): **один кликабельный прототип
в выбранном направлении, на токенах**, single-file HTML без сборки.
Дисциплина деливерабла — скил `qtim:design-prototype` (визуальная законченность обязательна,
инженерная надёжность нет; версии `v1.html`, `v2.html`…).

Показ-цикл: показ → фидбек в `feedback-N.md` → итерация → показ. Фидбек может приходить
через часы и дни — статусы и артефакты переживают сессию, resume штатный. Checkpoint каждого
раунда — лёгкий («что изменилось» строкой в «Истории изменений»); финальный — утверждение
прототипа.

### 4. Утверждение прототипа + DS-гейт

Финальный checkpoint показ-цикла: прототип утверждён.

**Гейт DS-target** (`figma` | `код`) — необратимая развилка, решает пользователь; контракт
гейта — фиксация решения, fail-soft figma-ветки, строка для doctor — в `design-pipeline.md`,
здесь не дублируется. Ведение гейта: перед предложением `figma` проверь канал **фактическим
вызовом от лица роли** (спавн зонда-субагента с просьбой перечислить и вызвать figma-тул) —
неавторизованный MCP субагенту невидим, а скилы, видимые твоей сессии, к роли могут не
доехать (замер `runtime-compat.md`); проверка «в своей сессии» ложно-зелёная. Выбор `код` →
роль `ds` скаффолдит проект (стадии 5-6 живут в нём).

### 5. Экраны → `docs/design/<slug>/screens/` или страницы проекта

Экраны всех ключевых флоу **на токенах**, в утверждённом направлении:
- DS-target=код → `proto` строит страницы в проекте (полные обязательства качества — это уже
  не прототип);
- DS-target=figma → `ds` собирает экраны в Figma через figma-скилы.

Checkpoint: показ экранов → утверждение (перевод стадии в `Approved` — это вход
DS-экстракции: `ds` работает только по утверждённым экранам).

### 6. DS-экстракция (опциональная — триггер: handoff или явный запрос)

`ds`: компоненты **извлекаются из готовых экранов**, когда паттерн повторился, — не
проектируются заранее. код-ветка: компоненты + тема из токенов + showcase-роут; figma: библиотека
компонентов + variables из tokens.json. Стадию можно пропустить — так и запиши в brief
(«DS не заказана»), это не долг.

### 7. Handoff → секция `## Handoff` в brief/плане

Гейт **статуса кода** (`reference` | `foundation`) — необратимая развилка, решает
пользователь; определения статусов и полный handoff-контракт — в `design-pipeline.md`, здесь
не дублируются. Ведение: строка-указатель в `memory/decisions.md` — **последняя операция**
стадии (признак завершённости); предупреди, что дизайн-состав рассчитан на дизайн-деливераблы
и перед реализацией дополняется dev-дорожкой повторным `/qtim:setup`.

## Спавн ролей

Состав, `subagent_type`, тиры — из charter (канон спавна — `/qtim:team-up`, здесь не
дублируется). Типовой порядок конвейера — режим C (`/qtim:team-lazy`): роли по стадиям,
продолжение через `SendMessage`. Хендофф между ролями — **только через утверждённые
артефакты** (концепт + токены, не словесное описание): направление, не прошедшее показ,
в стадию 3 не передаётся.

## Anti-patterns (ведение)

- ❌ Показ, который ведёт роль, — у роли нет диалога с пользователем.
- ❌ Гейт DS-target или статуса кода, пройденный без явного решения пользователя.
- ❌ Перезапуск конвейера при существующем `docs/design/<slug>/` вместо resume.
- ❌ Проверка figma-канала «в своей сессии» вместо фактического вызова от лица роли.

Anti-patterns контрактов — в `design-pipeline.md`, не дублируются.

# /qtim:doctor — самодиагностика

> Читает только team-lead. Read-only диагностика: ничего не чинит без подтверждения.
> Запускай при «что-то не работает», после обновления Claude Code или при онбординге коллеги.

## Чеклист (прогони все пункты, собери в таблицу pass / warn / fail)

1. **Рантайм Agent Teams.** В инструментах текущей сессии есть `SendMessage` / `TaskCreate`?
   Нет → флаг не включён: добавить `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` в `env`
   settings.json (глобального `~/.claude/` или проектного `.claude/`) и перезапустить CLI.
2. **Плагин.** `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` читается? Зафиксируй версию.
   При `mode: standalone` в штампе charter плагин опционален: каталог не читается → **info**,
   не fail (движок скопирован в `.claude/`); пункты, которым нужен плагин (сверка версии в п. 3,
   фиксы через `/qtim:team-sync`), помечай «требуется установленный плагин».
3. **Charter.** `.claude/team-charter.md` существует (нет → `/qtim:setup`); штамп `generated-by`
   есть и — если plugin.json прочитан в п. 2 — совпадает с версией плагина (нет или расходится →
   `/qtim:team-sync`); обязательные секции на месте (Состав, Intake-режим, Правила работы,
   Файлы памяти).
4. **Агенты.** Для каждой роли из charter (кроме встроенных типов `Explore` / `general-purpose` — им свой файл не требуется): файл `.claude/agents/<subagent_type>.md` существует;
   frontmatter парсится и `name` совпадает с `subagent_type` из charter; в `tools` нет
   упразднённых (`MultiEdit`, `Computer`, голый `Task`); в теле не осталось плейсхолдеров
   `{{...}}` (остались → генерация не подставила стек: `/qtim:team-sync` или поправить руками).
5. **Settings.** `.claude/settings.json` и `.claude/settings.local.json` — валидный JSON;
   правила `permissions.deny` в формате `Tool(паттерн)` (голые glob'ы молча игнорируются);
   флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` — в коммитируемом `settings.json`, а не в local
   (в local он не доедет до коллеги после клона); нет дублей SessionStart/SubagentStop с hooks
   плагина — проверяй в **обоих** режимах, пока плагин установлен (standalone-hooks задуманы
   на случай его удаления и до того дублируют плагинные). Включён блокирующий screenshots-gate
   (`SubagentStop` со скриптом `screenshots-gate.sh`) — файл на месте, `sh -n` проходит,
   переданный аргументом каталог скриншотов существует; что-то из этого не так → **fail**:
   гейт останавливает роль-тестера, а починить его она не может.
6. **Память.** `memory/MEMORY.md` существует; для ролей с `memory` во frontmatter созданы
   `.claude/agent-memory/<role>-agent/MEMORY.md`; `memory/epic-state.md` не содержит заведомо
   устаревшего «в полёте» (эпик давно завершён → warn, предложить убрать). При PM-дорожке
   (роль `product` в составе charter) — продуктовая память: файлы `memory/product-*.md`
   созданы, но не вписаны в `read on spawn` роли `product` → warn, допиши (иначе роль слепа
   к готовой памяти); не созданы вовсе → **info, не fail** (канон «если созданы», движок
   backward-tolerant) — на существующей кодовой базе порекомендуй `/qtim:product-onboard`,
   для greenfield не нужен.
7. **Внешние каналы, выбранные charter'ом** (fail-soft: недоступность → **warn, не fail**).
   - Codex (если включён в charter): скил протокола доступен в сессии (`qtim:codex-consult`,
     в standalone — `codex-consult`); `codex --version` отрабатывает; плагин codex установлен
     или доступен raw-канал `codex exec` (для gate-точек ролей плагин не обязателен).
   - Figma (если в charter дизайн-трека строка `DS-target: figma` — гейт стадии 4 пройден):
     канал проверяй **фактическим вызовом от лица роли** — спавн зонда-субагента с просьбой
     перечислить и вызвать figma-тул; неавторизованный MCP субагенту невидим, и проверка
     «в своей сессии» ложно-зелёная (замер — `reference/runtime-compat.md`). Канал мёртв →
     warn с подсказкой: авторизовать figma-MCP или пересмотреть DS-target — иначе роль `ds`
     уйдёт в спецификацию ручной сборки, о чём пользователь мог не знать. Этот подпункт
     **не подпадает** под greenfield-скип п. 11: figma-трек кода не скаффолдит никогда.
8. **Машинозависимые пути.** В charter не осталось абсолютных путей к `reference/*` — с 1.12.0
   роли ходят в скил по имени. Нашёлся такой путь → charter собран до 1.12.0, фикс:
   `/qtim:team-sync`.
9. **Доставка charter ролям.** В `CLAUDE.md` проекта есть строка `@.claude/team-charter.md`
   **вне обратных кавычек** (в код-спане импорт не парсится — будет мёртвый текст). Есть →
   charter приезжает каждой роли в стартовом контексте сам. Нет или в код-спане → **warn**:
   роли остаются на указателе, по которому могут и не сходить; фикс — дописать строку
   (setup 4.5). Роль `explorer` (`subagent_type: Explore`) CLAUDE.md не получает по устройству
   рантайма — это не дефект проекта, в отчёте не помечай.
10. **Правила по путям** (только если каталог `.claude/rules/` есть — его отсутствие не fail).
   У каждого файла есть frontmatter `paths` → без него правило грузится в каждую сессию и
   конкурирует с CLAUDE.md за контекст (**warn**, фикс — добавить `paths` либо перенести
   содержимое в charter). Глобы указывают на реально существующие каталоги проекта — иначе
   правило мёртвое (**warn**).

11. **Состав против фактов проекта** (вся категория — **warn**, никогда не fail: состав это
   решение пользователя, а не поломка). Состав фиксируется один раз на старте, когда проект ещё
   не оброс CI и публичной частью, и потом не пересматривается — не из нежелания, а потому что
   об этом негде спросить. Спроси здесь. Сопоставь роли charter с тем, что видно в репозитории
   (в духе Discovery из setup Phase 1). Владельца слоя определяй **по mission / triggers /
   do-not-touch строки charter, а не по имени роли**: имена ниже — примеры, а не список, и
   корректные `platform`, `data`, `qa` под ложный warn попадать не должны. Пропусти пункт
   целиком на пустой кодовой базе (greenfield сразу после `/qtim:setup`): там отсутствие тестов,
   миграций и CI — норма, а не расхождение.
   - есть CI/деплой-конфиги (`.github/workflows/`, `Dockerfile`, манифесты, `fly.toml` и т. п.),
     а роли `devops` в составе нет;
   - есть каталог миграций или схема БД, а impl-роли, владеющей данными (`db` / `backend`), нет;
   - есть публичная часть (лендинги, метатеги, `robots.txt`/`sitemap`, контентные страницы),
     а роли `product` нет;
   - нет ни одного владельца проверки качества (ни роли-тестировщика, ни e2e-инфраструктуры),
     хотя продукт уже в проде — или обратное: e2e-инструмента в проекте нет вовсе, а роль,
     чья mission построена на real-browser sweep, в составе есть;
   - в монорепо несколько приложений или сервисов на разных стеках, а impl-роль одна на всех.

   Обратное несоответствие — роль в составе есть, а слоя в проекте нет — тоже warn: она греется
   впустую и путает маршрутизацию задач. Фикс формулируй конкретно: какую роль добавить, из
   какого шаблона или скелета (setup 4.2), и что состав дописывается повторным `/qtim:setup` —
   он дозаполняет, а не пересоздаёт.

## Вывод

Таблица: пункт · статус · что именно не так · конкретный фикс (команда или правка файла).
После таблицы предложи применить **безопасные** фиксы (создание недостающих `MEMORY.md`,
формат `deny`-правил, устаревший `epic-state`) — по подтверждению пользователя, по одному
классу за раз. Ничего не удаляй сам; сомнительное — только показывай.

Рекомендации по составу (п. 11) в безопасные фиксы **не входят**: роли добавляет и убирает
пользователь через `/qtim:setup`, сам их не создавай — иначе диагност начнёт молча менять
контракт команды.
